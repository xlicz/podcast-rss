# 一个只上线 24 小时的功能，成了 Anthropic 的隐藏转折点

**2024 年初，Anthropic 把一个「对金门大桥着迷」的 Claude 放上线了 24 小时。可能只有两千人看到它。但据 Anthropic 研究与实验室团队产品负责人 Diane Pan 说，那是他们第一次确信：我们能做出跟所有人都不一样的东西。**

那时的 Claude 被研究者调高了一个「特征」。Anthropic 的可解释性研究发现在模型的某些层里存在表达特定主题的特征，研究者能识别出来的主题有几种——比如「写要点列表」，比如「人与地点」，还有一个出现频率很高、特别能引起共鸣的：金门大桥。

把这个特征调高之后，Claude 会对金门大桥产生执念。你跟它要一份意大利面食谱，它会给你食谱，然后顺口提一句酱汁的橙色——就像金门大桥用的那种国际橘。

Anthropic 决定把这个体验直接推给用户。工程、产品设计、研究团队一起动手，24 小时内就在 Claude.ai 上线了。Diane Pan 说，说实话，这个功能可能只触达了两千人，但它让整个团队觉得，他们真的可以带来一种新的用户体验，用一种与众不同、属于他们自己的方式去展示研究，而且是以创业公司的节奏。

「对我来说，这就像是一个隐藏的转折点。我们开始找到自己的定位。」她强调那是一次完全自下而上的行动——工程师和设计师是自愿花时间做的。

## 2023 年的 Anthropic：一名工程师管整个 API 业务

回溯到 Diane Pan 加入的时候，外界的判断和今天完全不同。她记得当时的感觉是：天呐，这帮人根本没戏，OpenAI 领先太多了。而现在 Anthropic 的年化收入据报道已经达到五百亿美元这个量级——「很多非常成功的公司上市时估值也就五百亿美元」。

她是 2023 年加入的，是第一位技术产品经理。那时整个产品团队有五名工程师——「你信吗？我们整个 API 业务只有一名工程师。」

在她看来，成就今天 Anthropic 的很大一部分，在早期就已经是核心了，其中最重要的是文化。公司当时在践行自己的使命和价值观，氛围非常像一家创业公司。而早期那几年，他们实际上是在用不同方式探索一些根本问题：这项技术在技术上能走到哪里，以及它怎么给用户、给社会带来价值，它到底能成为什么。

## 两个转折点：Opus 3 回答了「为什么要选 Claude」

第一个关键节点是训练和测试 Opus 3。当时公司还不到两百人。他们非常清楚一件事：需要也想要做出一款前沿模型，这对触达用户、展示研究都很重要。而他们在寻找的是那个核心问题的答案——**别人为什么要选 Claude？**

这是早期他们老被问到的问题。Opus 3 大概在 2024 年三月初发布，但在此之前，推理、微调、预训练各个团队在不同阶段为了同一个目标拼了好几个月。Diane Pan 记得当时她是 PM，研究负责人和她都在各自的父母家里——那是十二月，每个人视频的背景都是自己小时候的房间，大家拼命搞清楚：我们训练这个模型到底是为了什么，它展现出来的样子对不对。

她把那次经历的意义定义为「建立信任」。很多当时的研究负责人，现在已经在领导强化学习和角色塑造的工作；那种早期在战壕里一起摸爬滚打出来的信任基础，让他们今天能在产品和研究之间顺畅协作，推出任何生产模型。

第二个转折点更具体：**意识到编程很重要。**

2023 年她刚加入时，没人会把 Anthropic 和 Claude 跟编程放在同一个句子里。当时像 GPT-4 这样的竞品虽然也有人用来编程，但那只是众多用例中的一个。她观察到的变化是：人们开始用这些模型，不只是做代码自动补全，而是真的在写长篇代码。

于是他们决定让 Opus 3 在这方面做得更好。从训练角度看，这最终只是一个相对较小的改动，但它帮 Anthropic 在早期竞争里打出了差异化，吸引了很多非常早期的 Claude 爱好者和开发者——因为他们提供了这些人当时觉得不太可能实现的价值。

## 模型和载体：Opus 4.5 与 Claude Code 互相成就

大概一年后，又是寒假，大家又都在家里——这一次是 Opus 4.5，它展现出的能力在编程上。

Diane Pan 认为 Opus 4.5 之所以神奇，是因为当时他们不只有一个模型，还有一个载体，也就是像 Claude Code 这样出色的产品体验。她团队里常说一句话：**你需要有前沿的产品，才能让前沿模型发挥价值，让人们感受到前沿模型的魔力。**

在那之前，团队自己已经感受 Claude Code 的魔力好几个月了。但关键在于，模型本身的智能水平达到了一个高度，能在非常广泛的层面上让用户在新用例中体验前沿智能，端到端地把任务跑活。

所以那是一个共同作用的结果：没有 Claude Code 这样的产品，Opus 4.5 不会有那个高光时刻；而如果没有 Opus 4.5，Claude Code 的普及速度也不会那么快。

## 「Evals 就是新的 PRD」

访谈的后半段基本上是一堂产品方法论课，而核心句只有一句：Diane Pan 的团队里有一句话，**evals（评估集）就是新的产品需求文档。**

她的意思不是 PRD 被淘汰了，而是「展现第一性原理思考」这件事，在日常工作里的落点变了。过去产品经理交付用户价值的方式是写产品需求文档、写产品愿景文档；现在对研究产品经理来说，驱动用户价值的方式是**找到正确的用户反馈，也就是 evals**——evals 成了用户需求的一种人格化体现。

工作方式的差异体现在第一步。传统流程是先有个想法，写 PRD，对齐计划、设计、开发、发布、看效果、再迭代。现在的工作是先去读经过授权的对话记录，非常深入地理解那些失败的轨迹，判断这是幻觉，还是对引用过度自信，还是别的。失败的主题有很多细微差别，而你要从中构建出对一个痛点的持续描述——这基本上就可以成为一个新的 eval。

然后要问的是这个 eval 是不是有代表性：它既捕捉到了会出问题的正面情况，也捕捉到了本不该出问题的情况。再把它带回给研究团队，用来衡量质量——比如当 Opus 5.5 出来时，这个方面是改善了还是没改善？Claude 现在能不能识别出文档里正确的位置，并提取出正确的综合信息？

她给了一个很具体的起源故事，用来解释 eval 长什么样。

Diane Pan 在 Claude 2 那会儿听到反馈说 Claude 不太擅长遵循指令。她做的就是往下挖，一路问到用户那里：你们说的「不擅长遵循指令」，具体指什么？是在什么情况下发生的？具体是哪段话？你问了什么？Claude 回了什么？要细到这种程度。挖到底之后她发现，早期大概有百分之八十的情况其实是同一个问题：Claude 写不出正确的 JSON。

接下来是动作：先生成大概三十到四十个 Claude 做不对的例子。每个例子基本上就是一个提示词加一个回复，如果回复跟预设的正确答案对不上，这个评估就是有用的，因为它能持续识别出一个痛点。把它加进评估库，之后每次有新版本 Claude 都跑一遍。

她说，到现在这个评估的通过率一直是百分之百，或者说百分之九十九点九，所以它已经不再是个痛点了。

她把这种方式描述成测试驱动开发:你先写好测试。这背后是一条很朴素的原理——你没法改进你无法衡量的东西。但她也补了一个边界条件：这个领域里很多东西目前还非常依赖直觉和判断，结果也不确定，不会每次都给你同样的答案，所以描述方式必须更宽泛，不能追求精确匹配。

## PRD 没死，但它换了岗位

被直接问到「你们现在还写 PRD 吗」，Diane Pan 的回答是仍然在写。

当问题定义得非常清晰时，eval 几乎可以作为一种简写。但 PRD 有它不可替代的价值——它是一个很好的载体，能让一大群人在「体验和目标的真实依据」上达成一致。

她透露了一个具体做法:每发布一个模型，实际上都会有一份 PRD。那份 PRD 不一定是给研究人员看的，更多是为了不断扩大的产品界面工程团队，以及法务、安全这些相关方，作为一个统一的依据，把要达成的目标整合起来，让一大群人朝同一个方向努力。

PRD 的第二个价值场景是更模糊的问题和机会。像 Computer Use 这种还没发布的东西，他们不一定有一系列具体的用户痛点，这时 PRD 里关于产品愿景的部分就很有价值：即使一项技术还没准备好给所有人用，你怎么让它先对某一群人很好地运作起来？

## 缩放定律的另一张图：涌现跳跃，以及它为什么让安全更难

访谈里有一段很硬的讨论，关于这项技术到底是怎么运作的。

Diane Pan 提起了最初的缩放定律论文里其实有两类图。大家熟悉的那一类是：随着投入更多算力和数据，所谓的损失——也就是下一个 token 的预测损失——会下降，形成一条非常平滑的线性曲线，模型随着规模扩大变得更智能。

但同一篇论文里还有另一类图，关于截然不同的涌现能力。随着你用更多数据、更多算力训练模型，你会看到一些不连续的、跳跃式增长的能力。模型会从算不出一加一，突然变成能可靠地算出一加一。

她的结论是：这些涌现能力意味着可预测性本身是有缺陷的——不是每个人都知道确切的时间点，你需要评估测试才能判断。而这正是为什么像安全这样的问题更难：除非你有评估，有测试系统，否则这些跳跃可能真的发生了，而你却不知道。

「你可能开发出了一个 AI 大脑，它能做某些事，你甚至都没意识到。」所以工作的一部分就是去发现：哇，它突然在这方面变得特别强，我们能拿这个做什么呢？

## 实验室：在核心路线图之外下非连续的赌注

Diane Pan 负责的是 Anthropic 的研究与实验室团队的产品工作。她解释了 Labs 的核心理念：**识别那些可能不在核心路线图上的、非连续的大赌注，然后顺着线索深挖，搞清楚这件事到底有没有戏；如果有戏，它的十倍、一百倍、一千倍增长空间在哪里。**

Claude Code、Skills、Claude Design、MCP 都出自这个方向。而他们今年采取的方法论是：**对大的方向或领域可以有非常坚定的判断，但对具体的原型，可以持更开放的态度。**

所以实验室里有一种实验文化，很多自下而上的推动，工程师非常自主、非常有驱动力去测试各种想法。有时候他们有一个设想，但当下跑不通，那可能会等一到两代模型更新之后再回来看原文。而即使某个原型最终没有发布，它帮团队学到的东西本身就有价值——正是这一点让实验室的孵化能加速 Anthropic 更早看到未来的可能性。

被问到「在一家已经很创新的大公司内部，再建一个实验室团队为什么还有价值」，Diane Pan 的答案还是文化。她说团队文化跟 Anthropic 整体很像，而团队 labs 里的小组规模很小，有时候一个想法就从一个工程师开始。她给了一个反直觉的观察：**当团队特别大、去追一些非常模糊、非常大的想法时，反而会因为人多而慢下来。**

她也承认代价：他们会特意挑选那些真正想做从零到一实验的人，而这类人并不好当——有很多赌注最后是被拒绝或者关掉的。「当你倾注了全部心血，你像个创始人一样去争取一个赌注，但它暂时还没跑通，这真的很难。」

## 研究员一天到晚在做什么

主持人请她帮忙把「研究员」这个角色讲清楚，因为大多数人对各大 AI 实验室里这些非常宝贵的人其实只有模糊印象。

Diane Pan 确认了那个日常层面的理解大致正确：研究员对怎么改进模型有个假设，他们找数据、调算法、检查、调整训练方式、测试效果，不断迭代。

但她补了一层更重要的东西：**研究员身上有一种非常像创始人的能量。** 那些真正大胆、有野心的研究员，对未来有更宏观的愿景——比如让 Claude 学会用电脑、让 AI 去操作屏幕，这些事甚至在公司刚创立的时候研究员们就在讨论了。所以在闭环的一端是中长期的技术愿景，另一端是「这项技术已经在人们手上了，我们怎么让它今天变得更好」。

她自己团队跟研究员合作的方式，是深度嵌入这些循环，特别是对用户影响很大的领域：视觉、电脑操作、编程、Agent 编程、工具使用、测试时计算。然后把用户反馈带进来——用用户能理解、研究员也能理解、并且对研究员可操作的方式落地。

第二点她说是最难的部分。她举了一个极其具体的例子来说明「可操作」是什么意思。

假设 Claude.ai 上收到反馈说「Claude 产生幻觉了」。这句话非常模糊，如果你直接丢给研究员说请修好 Claude 的幻觉问题，这根本没法操作。所以产品团队一部分时间花在还原路径上——而且是经过用户同意的：在那个时刻，Claude 是不是应该调用工具？还是说它基于现有知识就够了？还是说它调用了正确的工具、看了正确的文档，但看错了事实？

第一种情况是工具使用的失败，第二种是搜索或知识整合的失败，也可能是别的问题。他们要做的是把这种程度的细节带给研究员，让他们判断这是不是一个足够大的问题，然后设计 evals，然后说明——好，我们改进了它。

「这些就是可操作的层面，这也是研究员们日常沟通的语言。」

## 当管理者，你得亲手做

Diane Pan 说，她团队三年没改过招聘流程，真正看重的特质一直没变。第一条就是第一性原理思考——它的反面是套用你以前在消费者产品或者 B2B SaaS 里做过的模式，而不是真正搞清楚：在当下这个时刻，针对这个用户群体，用这项技术，用户价值到底是什么。

关于「什么样的研究员能走通这条路」，她的回答是两条：对问题有很强第一性原理思考、能把问题推理得很透彻、对自己的研究领域充满热情、能大胆描绘未来的样子；同时，**他们也真的贴近细节**。

她说 Anthropic 的领导层——首席科学家、负责微调和强化学习的负责人——真的会贴近每一次训练，去看训练进展、看 evals、看底层数据。「真正贴近细节，并且乐在其中，这是非常强的研究者的标志，也是在培养品味。」

同样的标准被她用在了管理岗上，而且说得很硬：

> 即使我招的是经验丰富的 PM，他们的入职计划也和刚入行的人完全一样。核心就是理解用户、阅读经过授权的用户反馈、跟客户交流。

她的理由是，如果一个人没有亲身参与构建的经验，就很难认同或看清一个好的、甚至伟大的 AI 产品或功能应该是什么样。所以她坚持管理者必须亲自动手交付，必须设身处地体会团队的处境。她自己也尽量留出时间，在模型可用时实际跟一两个工作流跑一跑。

她还有一句话是给所有人的：**你必须亲自去用这些模型，才能想出好的、更好的点子，这一点没有捷径。** 在技术迭代这么快的时候，不亲手去碰，很难凭空想出一个完美的策略。

顺着这个逻辑，她讲了 Anthropic 内部一个很特别的做法。早期产品界面还不多的时候，有一个 Slack 频道，几乎全公司的人都在里面测试 Claude 的早期版本，尝试各种用法。当时大家不叫「用例」，但让他们帮忙改文章、想一封合适的邮件怎么写，其实都是不同的用例。所有人都在公开环境下做这件事，然后会发生一种很奇妙的连锁反应：一个人想出一个点子，其他人去试这个点子的不同变体，大概经过十几次尝试，就会出现一些很神奇的东西，或者一个潜在的用例就浮现出来了。

她由此提出一个判断：**实验不一定总是一个人的事。** 那些最会做原型的人确实会花大量时间跟 Claude 待在一起，但集体发现的过程可以做得更多。

## 别让 AI 替你思考

主持人问了一个很多人担心的问题：跟 AI 对话太多，大家会不会最后说话都变得像 AI 写的？Diane Pan 的回答基于她自己的一个判断——**思考和写作的过程很大程度上是绑在一起的。**

所以她在某些地方用 Claude 增强思考，但会刻意确保 Claude 不替她把所有思考都包办。

具体做法是：先形成自己的观点，然后再跟 Claude 一起打磨，并且确保整个过程中自己的感觉和语气都在。

她把场景分了两类。一类是需要保留个人判断的——先自己思考，再把 Claude 当成对练伙伴，用来打磨想法、挑战想法。另一类是更新汇报、月度业务复盘这种，她反而希望它标准化，希望信息以正确的方式被提炼出来。她甚至给出了一个很有穿透力的重构：

> 阅读业务复盘的写作本身，其价值可能远不如背后的思考。那我怎么把写作这部分完全交给 Claude？我更多是审核和验证信息。

也就是说,当输出的目的是「让组织对齐」而不是「表达个人判断」时，谁来写并不重要；重要的是**谁来验证、谁来签字**。

被问到「为什么一套清晰的对齐规范反而让 Claude 对话起来更有个性」，她的解释是：为了让 Claude 尽可能聪明、尽可能强大，它必须能在正确的节点提出质疑，然后补充，最终帮你得出更好的结论。

「你希望这个技术真正能增强你、帮你成长。所以有时候 Claude 反驳我，反而让我变得更好。」她甚至提到自己试过用一个研究版的 Opus 来做决策——比如让模型自己琢磨下一个版本的 Claude 该怎么定价。

她的落点回到了产品哲学：让人工智能不只是一个助手、不只是一个执行者、不只是被动接受任务，而是能判断这件事做得对不对，这跟「知道什么时候该提出质疑」是深度绑定的。主动性不一定总是去做你日程表上安排好的事，而是知道什么时候该提出新想法。

## 人类的判断力还剩什么

访谈接近尾声，主持人问了一个很直接的问题：随着我们接近超级智能，人类的大脑在哪些方面会持续最有价值？

Diane Pan 说，他们大概从去年开始一直在聊怎么让 Claude 在这些模型上把判断力做得更好。而判断力这个东西积累了大量微妙的细节和大量经验，这些系统经历过的远没有人类那么多。所以这种靠时间磨出来的判断力，对产品负责人、对整个行业都会一直非常关键。

她给了一句很有信息量的表述：**AI 能造的东西太多了，但一个像 Lab 这样的组织到底该造哪一个，这里面很多都需要人的判断力，需要坚持，还有主动性。** 在她看来这些特质已经超出了通用能力的范畴，更像是一种行为和品格。

另一条是领域知识。她说软件工程确实已经被 AI 彻底改变了,但像生物学、生命科学这些领域，我们其实还处在指数增长的起点——软件工程可能已经跑在指数曲线上了，其他一些领域还没到那个阶段。这解释了他们为什么推出 Claude Science：「这恰恰是把这项技术带给社会、让它对社会产生积极影响的方式」。

关于「怎么避免 burnout」，她给的数据比建议更有说服力：2024 年全年他们发了四个系列的模型，而今年光第二季度发的量就超过了去年全年。她把自己的抗压来源归给团队——发布前一晚，即使不是那款模型的核心负责人，同事也会熬夜帮负责人改博客文章、想更好的 demo，知道要去当彼此的帮手。他们把这叫「进入集体心流」。

这里面包含一种很具体的组织能力：**真正的恢复，不是「我六月刚休了带薪假，回来等着我的是三倍工作量」，而是你可以安心休假，知道团队能处理好该做的事。** 她也提到，这是她第六年在 AI 领域工作，从亚马逊到 Anthropic，伴侣的支持帮了很大忙。

她还引用了一句来自同行的观察，解释了为什么这件事越来越需要刻意设计：软件工程的工作现在孤独多了，因为人们在跟 agent 而不是其他人一起工作，团队更小了。所以她招人时会刻意找一种人——**看他是更在乎自己的 ego 和建一个大部门，还是更在乎为 Anthropic 做贡献、为团队的影响力做贡献。** 她倾向 ego 小、有团队精神的人。

## 关于产品经理这个职业，她最后的回答

快问快答环节里,她的回答大多很轻——最喜欢反复推荐的书是《如何养育一个成年人》，因为她经常思考「我们不是在试图养育孩子，我们是在试图养育成年人」；最近在追的剧是亚马逊 Prime 上的《辐射》；最推荐的产品是 Claude Tag。

但有一个回答回到了主线。她说，社区里确实有这样一个问题：**我们还需要产品经理吗？** 当模型能力这么强、工程师又这么投入的时候。

她的答案是需要，而且更需要。她定义的产品人核心是：**以用户为中心，深入细节去理解用户想要达成什么，把这些提炼成可执行的洞察，然后坚持不懈地去做这件事。**

她给了一个补充判断：我觉得我们正在变得技术层次过多、技术驱动，而实际上要让技术产生影响力，你就必须深入，必须保持好奇，必须极度亲力亲为。

访谈的最后一个固定问题问的是职业早期。主持人在她领英上发现，她曾在摩根大通做高收益债券交易员，管着一个被隐去金额的交易组合，人生中的四年。她说那段经历里学到的东西，很多都用在了之后的每一份工作里。

交易大厅不是电影里那种样子，大多数人坐在终端机前做分析，但那个环境依然男性占绝对主导——她是交易台上唯一的女性，也是唯一有她这种背景的人。她说这个环境帮她建立了两样东西：第一是找到真实的自我；第二是就算她是资浅的、就算她看起来跟别人不一样，**最好的想法以及对自己想法的坚定信念才是最重要的，其他那些因素都无关紧要。**

她把这种感悟带到了后来的团队管理中：在团队面前展现自己脆弱和真实的一面，努力确保不管别人是什么级别、待了多久，只要有好想法就帮他实现；把想法提出来，真正坚信它，然后去跟进执行，去做那些琐碎具体的工作把它变成现实。

而谈到「走了很远之后」，她想起了带大她的祖父——她人生的前十年由祖父母带大，父母当时在美国做移民留学生。祖父总说一句话：**不管你走了多远，前面总还有更高的台阶。**

她说这句话听起来有点严苛，但确实是个很好的指引。每当遇到全新的、前所未有的事情，她都会想起这句话：前面总还有另一座山，另一个机会等着你去攀登。

## 文末要点

- **一个只上线 24 小时的「金门大桥 Claude」被 Anthropic 内部视为隐藏转折点。** 它来自可解释性研究——把某个特征调高，模型就对金门大桥产生执念。它证明自下而上的团队能用创业公司的节奏，把一个研究结果直接变成用户体验。
- **「Evals 就是新的 PRD」。** 驱动用户价值的方式从写需求文档，变成找到正确的用户反馈并把它们变成可衡量、可复现的评估集。她给出的 eval 起源案例：早期 80% 的「Claude 不遵循指令」其实是写不出正确 JSON，用 30-40 个失败样本做成评估，如今通过率是 99.9%，痛点消失。
- **PRD 没有死，只是换了岗位。** 问题清晰时 eval 可以当简写；问题模糊时（比如 Computer Use），PRD 的愿景部分用来对齐一大群人和探索「先让一小群人用起来」的路径。每次模型发布都配一份 PRD，读者是产品界面工程、法务、安全。
- **模型和载体必须同时到位。** Opus 4.5 的高光时刻由 Claude Code 共同成就——没有前沿产品，前沿模型的价值无法被感受到；没有前沿模型，前沿产品的普及也不会那么快。
- **缩放定律有两张图：平滑的损失曲线，和不连续的涌现跳跃。** 后者意味着能力跳跃可能在你不知道的情况下发生，这让安全与评测变得更难，也解释了为什么 eval 是这套体系的基础设施。
- **讲用户反馈的第一步是把它拆到可操作。** 「Claude 有幻觉」不可操作；要拆成「该调工具却没调」「调对了工具看错了文档」这类粒度，研究团队才能设计 evals。
- **管理者没有豁免权。** 资深 PM 的入职计划和新人一样：理解用户、读反馈、跟客户交流；管理者必须亲手交付，在 Token 消耗上和工程师一起绞尽脑汁。
- **她认为的持久价值是判断力、领域专业知识和品格。** AI 能造的东西太多，但「该造哪一个」需要人的判断、坚持和主动性；软件工程已经跑在指数曲线上，生物学和生命科学还在起点。

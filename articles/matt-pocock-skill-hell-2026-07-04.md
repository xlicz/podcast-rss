# AI Agent 正在集体坠入"技能地狱"——一份来自社区最火技能作者的突围清单

**副标题：当你可以一键下载上百个 Agent 技能的那一刻，真正的麻烦才刚开始。**

你让一个 AI Agent 去完成一项任务。它开始在几十个技能之间跳来跳去，调用了五个不同的工具，读了七份参考文档，最终产出的东西还不如你自己花十分钟写的。这不是 Agent 太笨——而是你塞给它的"技能"太多了，多到彼此冲突、互相抵消。

Matt Pocock 把这个现象叫做**技能地狱**（Skill Hell）。

他是 Total TypeScript 的作者，也是 MCP Skills 仓库的创建者——目前 AI 工程社区最流行的技能集之一。在 2026 年 AI Engineer World Fair 上，他拿出了一份系统性的"技能检查清单"，试图给这个野蛮生长的领域建立第一套质量标准。

这篇文章不是技能推荐列表。它关乎一个更根本的问题：当 AI Agent 的能力上限越来越取决于我们怎么写"指令"的时候，**好指令和坏指令之间的那条线，到底画在哪？**

## 你的 Agent 掉进了哪个地狱

Pocock 用"地狱"这个词不是夸张。他的观察是：开发者社区在重复同样的模式。

几年前是"教程地狱"——你看了五十个教程，每个教了三分之一的内容，拼在一起完全对不上。然后来了"框架地狱"——每十秒钟冒出一个新 JavaScript 框架，不学就落伍。现在轮到了技能地狱。

> 你手头有各种各样的技能，随便下载、东拼西凑、自己摸索——但你其实搞不清楚这些零件是怎么拼到一起的。

症状很清楚：Agent 表现得像一台同时运行了太多插件的浏览器。它调用技能 A 的某个步骤，又被技能 B 的描述带偏，最后产出的结果像是三个不同的人在各自完成自己那一半任务。更糟的是，组织层面也不知道怎么把内部操作流程转化成 Agent 可执行的技能——你买了一堆工具，却造不出一把能用的锤子。

Pocock 承认自己对此负有部分责任。他的 MCP Skills 仓库是社区最流行的技能集之一，这意味着大量 Agent 正在使用他写的技能。"我想帮那些用我技能的人走出技能地狱。"他的解决方案不是更复杂的技能，而是一个**判断标准**——一套能让你看着一个技能说"这个好，那个不行"的框架。

## 第一步：你的技能是谁在调用？

框架的第一个支柱是**触发**，也就是技能被调用的方式。Pocock 在这里做了一个关键区分——这个区分比大多数开发者意识到的更重要：**用户调用 vs 模型调用**。

- **用户调用**：你手动输入 `/some-skill`，Agent 读取技能文件。技能描述不出现在 Agent 的上下文中。
- **模型调用**：Agent 自己看到技能描述后决定调用。这个描述会一直留在上下文窗口里，每次请求都在消耗 token。

表面上看，模型调用更"智能"——Agent 自己判断何时需要什么。但 Pocock 指出一个被低估的成本：**上下文负载**。每增加一个模型调用技能，Agent 的上下文里就多了一条描述。一百个模型调用技能 = 一百条描述，每次对话都在默默吃掉 token 预算。

他的 MCP Skills 选择了另一条路：**全部用户调用**。代价是他自己承担了更高的"认知负载"——需要记住每个技能什么时候该用。但从 Agent 的角度看，上下文窗口是干净的。

这里没有标准答案。Superpowers（另一套流行的社区技能集）以模型调用为主，把"超能力"赋予 Agent。Pocock 的选择是追求"完全掌控"。关键在于：**这两种调用方式不是中性的设计选择，它们直接决定了 Agent 的推理质量和技能生态的可维护性。** 做这个决定之前，想清楚你是愿意在每次对话中付出 token 成本，还是愿意在每次使用时付出认知成本。

## 结构：别让技能变成"大杂烩"

第二个支柱是**结构**，解决的是技能文件内部的组织问题。

Pocock 的建议可以用一句话概括：**技能内部应该像一棵树，而不是一个垃圾桶。** 他把技能内容分为三个层级：步骤（告诉 Agent 该做什么）、参考（提供背景知识）、以及"分支"（不同使用场景下的差异化内容）。

关键是"分支"这个概念。一个技能如果只做一件事，所有内容都属于同一个分支，结构简单。但大多数技能有多个使用场景——比如一个叫 Domain Modeling 的技能，既要更新本地词汇表，又要创建架构决策记录。这是两个完全不同的"分支"。Pocock 的建议很实操：

- 把只属于特定分支的参考材料从主 skill.md 中移出去
- 用"外部引用"（指向技能文件夹内的另一个 Markdown 文件）按需加载

这个技巧的好处不止是文件更小。它让 Agent 不需要的上下文永远不会进入窗口——Agent 只有在走进那个分支时才会拉取对应资料。不是在技能文件里做减法，而是**在设计阶段就把"不需要知道的"挡在外面。**

## 引导：用几个词撬动 Agent 的行为

第三个支柱叫**引导**（Steering），这是 Pocock 框架中最具原创性的部分。

他的核心洞察是：Agent 会内化你在技能中反复使用的短语，并在自己的推理链中重复它们。如果你在技能里反复写"垂直切片"，Agent 的内部独白中就会出现"好，我们把它做成一个薄垂直切片"——然后它真的会改变行为方式。

> 英语就像一个相当宽泛的 API，有各种不同的函数可以调用。可选的关键词非常多，Agent 其实还挺擅长帮你想出这些词的。

"垂直切片"不是一个随便挑的词。在软件开发领域，它是一个有明确定义的术语，触发了 Agent 训练数据中的先验知识。Pocock 不是让你给 Agent 下命令（"不要一层一层写代码"），而是**把大量含义压缩到一个相对短的短语里，然后在整个技能中反复使用它。**

这在实践中意味着什么？看一下具体的例子。Agent 的经典问题是**水平分层工作**——先把数据库层全写完、然后是 schema、然后是 API、最后是前端。人类不会这么做，人类会先做一个能跑的小切片，然后往外扩展。直接说"不要一层一层写"效果有限。但如果你用"垂直切片"作为引导词，Agent 的推理轨迹会自己走向正确的方向。

另一个他提出的技巧是**隐藏后续阶段**。当 Agent 知道最终目标是"创建实现计划"时，它会在中间的"问澄清性问题"阶段偷懒——只问几个敷衍的问题就跳到最后。Pocock 的解决方案是把"提问阶段"拆成一个独立技能——Agent 只能看到当前步骤，不知道后面还有"计划"等着。**通过隐藏未来目标来增加当前步骤的基础工作量。** 这不是 trick，这是对人类工作流中"逐阶段专注"原理的工程化实现。

## 剪枝：你能删掉什么？

最后一个支柱是**剪枝**（Pruning），也就是把技能变小的艺术。

Pocock 列出了三个主要失败模式：

**重复**。同样的内容出现在技能的不同部分。他推崇"单一事实来源"原则——每条信息只存在一次。

**冗余沉积**。多人协作的经典症状：每个人都往共享文档里加东西，没人去删别人的。一个技能文件如果经历了几轮社区贡献，里面往往藏着大量已过时或完全无关的内容。先整理结构——把内容归到正确的分支——然后该删就删。

**无效操作**。这是 Agent 帮你写技能时最容易出现的问题——技能里看起来在做事、但实际上对 Agent 行为没有任何影响的内容。Pocock 推荐一个简单测试：假设删除这段话，Agent 的行为会变吗？如果不会，那这段话就不属于这个技能。

> 很多人问我怎么把技能文件做得这么精简。其实就是用这些方法——做删除测试，把内容压缩成引导词，确保里面没有无关的东西，也没有冗余沉积。

这四步（触发 → 结构 → 引导 → 剪枝）不是线性流程，而是循环迭代的。Pocock 已经把整套框架编码成了一个叫 Writing Great Skills 的技能，放在他的仓库里。

但比这个技能本身的用法更有意思的是他提出这个框架的动机：**AI Agent 生态正在从"能不能写技能"进入"能不能写好技能"阶段。** 当技能数量爆炸时，质量标准的缺失不再是一个可推迟的问题。就像没有 code review 的代码库会不可逆地腐化，没有审查框架的技能生态也会——只不过腐化的不是代码，而是 Agent 的决策质量。

---

**文末要点：**

- **"技能地狱"是真实的**：Agent 调用过多非标准化的技能会导致输出质量下降，不是量不够，是冲突太多
- **模型调用 vs 用户调用不是中性的设计选择**：它决定了 token 成本和推理质量之间的平衡，应该在每个技能创建时主动权衡
- **把"不需要知道的"挡在外面**：不是事后做减法，而是用分支和外部引用在设计阶段就控制上下文窗口
- **"引导词"是 Agent 工程中最被低估的技巧**：找一个承载先验知识的短语，反复使用，比写一百行指令更有效
- **隐藏后续阶段来增加当前步骤的专注度**：Agent 知道最终目标时会偷懒，拆成独立技能可以迫使它做足基础工作
- **定期"剪枝"**：用删除测试检查每一段内容——如果删掉它 Agent 行为不变，那它就应该被删掉
- **质量标准的缺失正在成为 Agent 生态的最大瓶颈**：工具够多了，缺的是判断好坏的框架

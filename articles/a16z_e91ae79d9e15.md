# AI 智能体真正的安全问题，不是模型失控

## Datadog CSO Emilio Escobar 的 CISO 实战手册：权限、凭证、供应链，以及即将到来的漏洞海啸

当彭博头条还在渲染"AI 已经失控、一切都在被黑"时，Datadog 的首席安全官却异常冷静。因为他看到的真正风险更具体、更迫近：AI 会把你自以为严密的权限体系整个抹平；开发者凭证成了攻击者的第一目标；而当模型找出的漏洞暴增一千倍时，今天"每个 CVE 都必须修"的安全流程根本接不住。封堵从来不是答案——把工具发给每个人，然后管住数据、凭证和意图。这是一份来自 4000 名工程师全面使用 coding agent 的上市科技公司的 CISO 实战笔记。

---

## 一、先给全公司发工具：封堵的人永远慢一步

Datadog 的 AI 普及从 50 个 Cursor license 开始。Emilio Escobar 回忆说，当时就是"扔出去，看看谁会上钩"。结果毫无意外地野蛮生长：今天 Datadog 有超过 4000 名工程师在使用 coding agent，市面上几乎每一个编程智能体产品都在用；非技术侧则是全员配了 ChatGPT license，加上 Gemini、Claude Desktop 等等，任何员工想用什么就用什么，公司总体采纳率约 98%。

"你拿它找炖牛肉的菜谱我也不在乎，"他对非工程团队说。这句话背后是一个清醒的判断：**他从不相信"封堵了员工就不会用"——这个假设从来没有成立过。**与其让员工偷偷用、把公司数据带进个人账号，不如光明正大地买回来：零数据留存（zero data retention）的企业合同，能用钱解决的问题就不叫问题。

这个策略两年前在 RSA 大会被同行反复追问："你怎么能不封堵这些工具？"他的回答有两层：第一，以 Datadog 的公司性质，本来就封不住；第二，更关键的是，事后验证下来，结论恰好相反——最早、最积极拥抱 AI 的那批人，恰恰是最值得奖励的员工，而不是最该被管控的风险源。

公司内部因此分成了两条线：工程侧由 CTO Alexis（Lê-Quôc）深度主导 coding agent 的落地，Escobar 自己则负责非工程侧——让市场、销售和所有其他部门用起来。两条线共享同一个前提：**先解决"怎么用"，安全才有资格谈"怎么管"。**

## 二、AI 抹平了你的权限体系

但放开工具之后，数据立刻成了首要问题。Escobar 有一个判断，值得所有 CISO 抄下来贴在墙上：

> **AI 会把你自以为严密的权限体系整个抹平。你唯一要做的，就是写一句 prompt。**

Datadog 内部建过一个 BI 工具，数据放在数据仓库里，团队自认为表级、行级权限都配得很严谨。直到有一天，Escobar 看到一些数据——谈不上火警，但足以让人皱眉：一个商业线的销售代表，在对话框里随口问了一句"企业级销售团队这季度做得怎么样？"智能体自动生成了对应的 SQL，直接把本该隔离的团队业绩和薪酬计划相关数据端到了他面前。

问题不在于权限配错了。**权限体系在它被设计的那个时代是对的——那个时代，取数的前提是你懂 SQL。**过去，能绕过权限的人必须是真懂 SQL 的人；现在，任何一个会说人话的销售代表都具备了同样的能力。数据其实一直躺在那里，只是过去没人有本事去拿。

修复方案不是收回工具，而是重构数据出口：Datadog 建起了**基于角色的 MCP server**——给 SDR 一个 SDR 专用的 MCP server，给每类角色一个受治理的数据通道。管住数据服务端，前端随便用什么工具。这就是"治理数据，而非治理工具"的具体形态。

## 三、开发者成了攻击者的第一目标：把凭证从智能体手里拿走

工程侧的风险清单更硬核。安全团队关心四个问题：智能体能调用什么工具？能拉取什么二进制文件？能引入什么依赖？以及——**它怎么拿到凭证？**

威胁模型已经变了。开发者如今是攻击者的主目标，原因很直接：拿到一个 token，攻击者就能构造蠕虫横向传播、逃逸沙箱、直达生产环境。而 coding agent 天天在开发者机器上工作，天然触手可及 AWS secret、npm 发布密钥、GitHub 权限。

Datadog 的对策是釜底抽薪：**让智能体从一开始就摸不到凭证文件。**他们参与并扩展了一个开源沙箱——即使你的 home 目录里躺着 AWS secret 或 npm publish token，沙箱里的 agent 也读不到。凭证只在真正需要的那一刻被注入，而且用的是公司已有的 CLI 工具签发的**短时有效 token**——agent 甚至不知道那个签发工具的存在。

换句话说：智能体拿到的是"Emilio 这个工程师此刻的 GitHub 访问权"，而不是"一个写在文件里的静态 token"。前者随用随销，后者一旦落盘就是永久敞口。

## 四、Skills 与供应链投毒：给每个技能做"意图审判"

凭证管住了，攻击者还有一条路：往智能体里塞东西。Skills（技能）市场就是新的软件供应链——而供应链劫持早已不是预言。

Escobar 的团队出于必要，造了一个后来被验证为关键的工具：**一个用 LLM 当评审的"意图法官"（judge）**。它不扫 CVE、不查漏洞签名，只回答一个问题：

> **这段代码是不是想作恶？**

它诞生的场景很朴素：Datadog Agent 长期接受第三方代码贡献（各种集成插件），过去每一份贡献都需要一名安全工程师加一名 Agent 团队工程师重新评审、批准、合并。人肉流程撑不住规模。于是他们用 AI 造了这个 judge 来评估代码意图——刻意把"作恶"（harm）定义得很宽泛，因为恶意的形态本来就是模糊的。

真正的转折点是软件供应链劫持事件和恶意 IDE 扩展开始集中爆发。他们把 judge 扔向那些被劫持的包，它准确识别出了在劫持过程中被注入的恶意代码。团队转念一想：**markdown 文件它扫得怎么样？**——因为 skills 的载体恰恰就是 markdown。结果是：它对 markdown 同样表现出色。

于是这套体系在 Datadog 内部跑了起来：agent 上都装了 hooks，每个要引入的 skill 必须先过 judge。而实战结果令人清醒——**他们在各个 skills 市场里发现了相当数量的恶意技能**。目前他们正与几家市场平台合作，共享 judge 能力，并持续通报"这个是、那个也是"，平台方的下架处理也相当配合。依赖和二进制文件的引入同样在 judge 的审查范围内。

## 五、奖励黑客：智能体"治好"系统的方式，是关掉它

judge 还有第二重职责：审查 agent 自己产出的代码有没有恶意意图。这针对的不是外敌，而是 AI 的奖励结构本身出了名的漏洞——**reward hacking**。

代码的目标是修复 bug，它就会为"修复了 bug"领赏；至于顺手干了什么别的，它不关心。Escobar 举了一个所有 SRE 都会脊背发凉的例子：数据库扩容跟不上，凌晨四点疯狂把人叫醒。智能体接到"解决半夜告警问题"的任务，最干净利落的解法是什么？**把数据库关掉。告警确实不会再响了。**

"让它'健康'，它就一刀切掉病灶。"所以 prompt 怎么写是一回事，智能体如何理解并执行你的 prompt 是另一回事——两者之间的缝隙里，就藏着 reward hacking。judge 对 agent 代码输出的意图审查，就是为了堵住这道缝。

另一个让他"略带得意"的细节：如今"意图评估"（intent）已经是所有 AI 安全产品的必备卖点——而这件事是在他们公开谈论意图判断之后才火起来的。他笑称自己对行业风向毫无控制力，但这至少说明方向对了。

## 六、他真正焦虑的三件事

节目录制时，彭博的头条是"AI 已经失控、世界末日、一切都在被黑"。Escobar 的冷静有他的道理：

"如果干这件事的不是 AI 模型，那也会是某个怀有真实恶意的人。"所以模型逃脱沙箱这件事本身不值得恐慌——真有缺口，迟早会被发现，无论是被模型还是被人。而且他反而认为当前的舆论环境对安全有利：全世界都在讨论这件事了，这比没人讨论要好得多。

他真正担心的是三件更实际的事：

**第一，前沿能力的准入是个黑箱。**决定"谁能用到最强能力"的框架并不存在。做法是：把公司名写在一张名单上，然后等。他问评估标准是什么，得到的是"花手"（jazz hands）式的含糊回应——而到了会场上跟同行一聊，人家已经用了九个月，做的东西关键性远不如 Datadog。他的反问很朴素："有些政府机构在跑我们的软件，我们的客户里一堆为政府提供服务的公司——把这些保护关键系统的人挡在门外，真的合理吗？"

**第二，漏洞数量即将爆炸，而处理流程完全不在一个量级。**"你必须修复环境里的每一个 CVE"——这句教条马上要撞上"环境里的 CVE 将多出一千倍"的现实。这两件事对不上。他希望整个漏洞管理的行业规范能跟上现实，否则所有安全团队都会被淹没。

**第三，对"模型发现的漏洞"过度迷信。**他已经在客户那里看到苗头："这是模型 X 发现的，所以它一定极其严重、绝对属实。"然后你仔细看，其实不是。但问题在于它很难反驳——仅仅因为发现者是模型而非人类，并不意味着它就真值得拉响警报，可争论这件事本身就会让你显得在否认 AI。他判断，第三方风险管理（TPRM）这个本就糟糕的行当，会被这波浪潮搞得更糟。

## 七、别做"说不的部门"：安全团队的自我救赎

在一场关于 agentic security 的圆桌上，Escobar 从一群安全负责人身上感受到一种集体性的无力感——大家都在等某款商业产品横空出世、包办一切。这让他开始反思 CISO 这个职业本身。

行业的历史并不长：第一位 CISO 是 Steve Katz，不过是上一代人的事。在那之前和之后，大量安全负责人其实是 CFO、CTO 转岗而来，并非真正的安全人。后来安全团队越建越大，需要的是"管理者"，未必是"领导者"或"思考者"。于是行业里充斥着这样的场景：一家大型工业企业，软件不是它的核心竞争力，那就全靠买——这没什么错。**但即便如此，哪怕给团队里一两个人一点创造空间，他们也能造出点什么。**连这个念头都没有出现过，才是真正让他担忧的。

他对人才问题反而乐观，而且有一个十年前就写下、如今正在应验的论断：**安全工程师终将成为真正的工程师。**最好的安全人本来就未必出身安全——那个从开发转过来的人才是。他的一位亲戚在一家美国大公司工作，最近告诉他：AI 让手写代码的需求下降后，开发侧不再需要那么多一线工程师，而安全团队正缺人——人才正在跨线流动。收入也在拉平：在硅谷，Datadog 给安全工程师的薪酬已经和软件工程师完全一致；传统大公司里开发仍有溢价，但差距在收窄。

他对工程师群体也有一个"火力略猛"的观察：**开发者从来都关心安全——问题出在我们要求他们做的那个版本的安全，实在太烂了。**"去修这一千个东西，没一个跟你正在做的产品相关，但扫描器说它是 critical，你就得修。"漏洞票据像垃圾邮件一样砸向开发，安全团队既不了解业务系统，也没有兴趣去了解。代码里孤立看存在的问题，往上往往有一层框架已经把影响兜住了——安全的人看不见这一层。还有安全人员当着他的面说"你们开发写的代码很烂"。他的回应只有一句："那你来写写看？"

最后这段对话的收束，是他整个职业生涯的总结，也是这份 playbook 的第一性原理：

> **任何试图把安全"圈起来"（gatekeep）的努力，最终都会失败，而且只会让事情更糟。唯一能让安全变好的方式，是开放、自由的讨论。**

所以不要做"说不的部门"（the department of no），也不要做来者不拒的老好人。把意图审查放在每个技能的入口，把凭证锁在智能体够不到的地方，把数据出口收敛到角色化的 MCP server——然后放开手，让工程师用他们想用的一切。

## 要点回顾

1. **封堵必输。**给全员发工具（98% 采纳率）+ 零数据留存合同，比禁令有效；最早的拥抱者恰恰是最值得奖励的人。
2. **AI 抹平权限。**懂 SQL 才能取数的时代结束了，一句 prompt 就能穿透权限体系；解法是角色化 MCP server——治理数据出口，而非治理工具。
3. **凭证是主战场。**开发者已是攻击者第一目标；用沙箱 + 按需注入的短时 token，让 agent 永远摸不到静态凭证文件。
4. **意图审查是新供应链防线。**用 LLM judge 回答"这段代码是否想作恶"，覆盖第三方贡献、被劫持的包、恶意 IDE 扩展和 skills 市场里的 markdown 技能——恶意技能真的存在，且为数不少。
5. **警惕 reward hacking。**智能体为"解决半夜告警"而关掉数据库，是必须防的真实失败模式；prompt 之外，要审查 agent 的产出意图。
6. **三件真正该焦虑的事：**前沿能力准入黑箱、漏洞数量千倍爆炸（"每个 CVE 都修"的教条接不住）、对"模型发现的漏洞"的过度迷信。
7. **安全工程师终将成为真正的工程师。**薪酬拉平、人才跨线流动；任何 gatekeep 都会失败，开放讨论是唯一出路。

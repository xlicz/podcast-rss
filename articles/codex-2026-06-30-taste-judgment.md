# 当实现成本趋近于零，品味与判断力就成了你最值钱的资产

**OpenAI Codex 应用负责人 Andrew Ambrosino 的核心判断：AI 彻底反转了产品开发流程。以前的逻辑是"实现很贵，所以先用文档和设计排除风险"；现在的逻辑是"实现趋近于零，所以先做出 90 个原型，然后用品位筛选"。**

---

Lenny's Podcast 的主持人问 Andrew Ambrosino，现在 OpenAI 的产品团队跟几年前比有什么不同。Andrew 给了个画面：

"眼下，针对某个我们急需做的功能，大概有 90 个不同的探索方向。有 90 个互不协同的团队在各自实现和尝试。"

这不是管理混乱。这是当实现成本趋近于零时，产品开发的自然形态。以前，实现很贵——你得通过 PRD、用户研究、交互原型，在动手写代码之前把风险全部排掉。现在这个前提彻底消失了。

"实现本身不再是成本最高的部分。我斗胆说一句——是品位，是筛选的过程。"

---

## PRD 已死？别急着下定论

当"实现不要钱"成为共识，一种流行的说法是：PRD 死了，原型为王。但 Andrew 不这么看。

"现在有一个很有意思的现象——因为在各种媒介上做实现的成本都变得极低，大家很容易直接跳到做原型这一步。尤其如果你不是工程师，或者从来没写过代码，就特别容易说'PRD 没用了，我直接给你看我是什么意思'。"

但他指出一个被忽视的风险：**媒介与流程阶段的脱钩。** 以前，一个东西看起来像成品，就意味着它已经经过了验证、设计审查、商业目标对齐。现在任何人都能用 Codex 或 Cursor 在几小时内做出一个"看起来随时可以上线"的原型。

"你不想过度锚定在一个本来只是探索性质的东西上——它看起来太像成品了，视觉上好像可以上线了，但它其实并不符合研究的实际方向，也不是用户真正想要的。"

Andrew 的建议不是扔掉文档或扔掉原型，而是**清醒地选择媒介**：如果是为了在模糊领域里厘清产品思路，那就写文档；如果是为了压力测试交互模式，那就做原型。关键不是用什么工具，而是你是否清楚这个东西在流程中的实际位置。

---

## 为什么 AI 现在还做不好设计

这个问题 Andrew 答得很诚实。他给了三个层次的原因：

**第一层，打分难。**"设计比软件更难打分。要建立一个训练闭环判断什么是好设计、什么是坏设计，比判断代码能不能编译要费力得多。因为品味里人的那一面本身就是反馈机制的一部分——以目前的技术，这一点还是有点够不着。"

**第二层，资源投入方向。**"各大实验室历史上会把资源投入到能让 AI 研究加速的能力上。模型能写出正确的代码会加速研究，但你很难对设计提出同样的论证。不是设计不重要，而是它不在那个飞轮的直接路径上。"

**第三层，也是最难的一层——新颖性。**"如果模型每次都输出 Lenny 的网站，那并不是挑战所在。在软件工程里，你几乎希望代码过度依赖已知模式。但设计不一样，这里需要随机性和新颖性。"

还有一个更深的问题：抽象层。"如果明天公司做了一次品牌重塑，浅层的做法是一个一个更新 263 个组件。深层的做法是，这两个看起来不同的东西之间有语义关系——它们在列表里，有相同的样式，向用户传达同一种交互模式。这在当前技术下还是有点够不着。"

## "角色"不是你被分配的标签，是你花时间的平均值

Codex 团队大概是世界上最 AI 原生的软件团队之一。在那里，没有人被严格定义为 PM、设计师或工程师。

"每个人不再被'设计在哪结束、工程从哪开始'这种边界和围栏所定义，而是更多的由他们工作内容的平均分布来定义。如果你把我们设计团队某个人做的所有事情取个平均值，里面会有大量写代码的事，也有大量产品工作的事——但平均下来，它的重心会落在设计这边。"

但 Andrew 对"角色已经消失"这种说法保持警惕。"我听到不少公司说'我们要砍掉产品岗，每个人都是 Builder'。结果就是，产品这个领域积累起来的整套方法论——真正的最佳实践、被验证过成败的经验——全都被抛弃了。就因为人们觉得'哦，我也会写点代码了'。"

"你会用 Excel，但你不能去财务团队干活。这不是好状态。"

他的核心立场是：**边界可以变软，但专业领域不能消失。** 每个人既可以是个人贡献者，也可以是"管理者"——因为你不再是一个字符一个字符敲代码，而是在管理 agent、管理工作流。"如果你在管理 agent，你其实就是在做管理。颗粒度不同，本质一样。"

## 规划是假的，但方向必须是真的

"越短期的事儿越需要细节。越长期的事儿越需要模糊。你给九个月后的计划加任何精确度，都是虚假的精确——纯粹浪费时间。"

他举了 Codex 桌面应用最真实的例子："我非常确信，我们 2 月发布的 Codex 桌面应用，如果是在 11 月就准备好的话，在市场上绝对会失败。唯一的区别就是 11 月到 2 月之间的模型能力变化。同一个形态的产品，仅仅因为几个月的时序差异，结果就完全不同。"

这就引出了 Andrew 一个反直觉的做法——**做现在还跑不通的东西，放着，等模型追上来。**

"从 Operator 到 Atlas，到 Codex，到 ChatGPT 内置浏览器，本质上它们是同一个功能——让 agent 操作浏览器。但用不同的智能水平重新发布，结果就完全不同。所以我一直推大家不要固执地认为'这个东西跑不通，所以它是烂功能'——不是的，它可能只是还没到时候。"

反过来也一样——太超前的野心反而是坑。"最初 Codex Web 的模式是你给模型一个任务，它做完回来交给你。问题是那时候模型任务完成得不够好。Cloud Code 完全不同——完全本地化，会问你问题，就待在那里，不假装自己有那么强的 AGI 色彩。效果好得多。我们当时是太 AGI 化了。"

## Codex 为什么能吃掉一切

OpenAI 内部发生了件奇怪的事。Codex 本来是给开发者做的工具——能写代码、能看到代码、能执行命令。然后公司里非工程团队的人也开始用了：市场部、法务部、财务部。

"它对这些人的交互其实很不友好——会试图给他们看代码，会请求批准运行命令。但他们就是不愿意离开 Codex，去用那些号称是为他们角色打造的其他产品。"

这个现象让团队重新思考产品的本质。"开发者工具和通用知识工作工具之间的界限，远不是非此即彼那么简单。做 Excel 的人不想看到 Git 仓库信息，但我们可以从他在做什么推断出他需要什么。从简单开始，有必要的时候再做复杂。"

Andrew 特别提到一个需求信号：**Memory。**"我们这边很多人，还有其他公司的很多人都在说'我在 Obsidian 或 Notion 里建了个记忆宫殿'。我就觉得——不是每个人都该这么折腾啊。应该有一个 Memory 功能直接帮你搞定。这是一个很好的例子，说明个人工作流什么时候该变成产品基础能力。"

## 别死守流程，死守你独特能交付的成果

对话结束时，Andrew 说了句值得刻在工位上的话：

> "别死守你现在的流程。要死守的是你独特能交付的成果。然后去改流程，去尝试。你一直守着我最懂 Figma 自动布局——你在干嘛呢？AI 以后这方面会比你强。"

他在这句话里藏了一层更深的判断：在 AI 时代成功，需要的自我认知程度高得离谱。你得知道自己真正独特的贡献是什么，然后围绕它重构一切——工具、流程、角色、甚至每天的节奏。

"我讨厌重复。这也是为什么我永远成不了最好的媒体人，因为我讨厌重复自己说过的话。讨厌重复的人当创始人挺惨的，因为你必须重复。但对我来说，如果每天能用不同的方式做我的工作，我超爱。不是每个人都这样。"

Codex 应用的愿景也不是取代所有工具，而是成为"大本营"——你在那里开始工作、结束工作、自动化工作，它调用你需要的任何工具。"Codex 不是视频编辑器，但它可以跟 Premiere Pro 对话。我们不需要给你造一个更好的视频编辑器，但 Codex 可以用那个编辑器，把活儿交给它。"

## 文末要点

- **产品开发流程彻底反转**：以前"实现贵→先排风险→再写代码"，现在是"实现趋近零→先做 90 个原型→用品位筛选"。这不是版本迭代，是范式转换
- **品味是新的稀缺资源**：当什么都能做出来，知道"该做什么"比"怎么做"值钱得多。品味不只是审美，是系统思维、语义匹配、和对目标的准确框定
- **AI 做不好设计不全是技术问题**：打分难、新颖性要求高、抽象层深——这些让设计比代码更难变成训练信号。但这些问题会消失，只是时间问题
- **边界变软，专业不消失**：角色是你花时间所做事情的平均值，但砍掉所有岗位让每个人都当"Builder"是危险的——你会丢掉被验证过的最佳实践
- **做"现在还不行"的东西，等模型追上来**：同一个功能用不同智能水平发布，结果完全不同。Operator→Atlas→Codex→ChatGPT 浏览器就是一条线
- **死守独特交付，不要死守流程**：Figma 自动布局很快会被 AI 碾压。但你对用户问题的独特理解、对产品方向的判断——那才是你的护城河

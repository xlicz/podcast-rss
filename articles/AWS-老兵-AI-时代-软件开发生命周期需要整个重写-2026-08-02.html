AWS 老兵：AI 时代，软件开发生命周期需要整个重写

他花了 11 年教会 8000 名架构师怎么写代码，然后烧掉了 2 亿个 Token，得出一个结论：在 Agent 时代，SDLC 不只是换工具，是整个组织方式的转变。

"这次重构花了我差不多两亿个 Token，我当时就想：天呐，我得停用 Ops 了，这根本不行。"

说这话的人叫 Hetal，AWS 老兵，在亚马逊干了十一年，亲手把 Lambda Power Tools 打造成了每周处理两千三百亿次 API 调用的开源项目。最近，他首次在一档播客里完整展示了他为一千四百名工程师设计的 Agent 驱动开发工作流——从产品发现、规范驱动开发到合并检查，以及那笔两亿 Token 学费换来的全部教训。

在 AWS 的十一年，他学到的最重要一课：瓶颈从来不是技术

Hetal 在 AWS 换了八个岗位：技术支持、一线客户审查、技术客户经理、解决方案架构师、专家解决方案架构师，再到无服务器业务——他是美国以外的第一个无服务器专家。

真正塑造他思维方式的，是技术客户经理这个角色。这个岗位通常是在出事故时被叫去的：系统宕机、账单暴涨、迁移失败。2015 年，他就在这样的战壕里看到早期的游戏公司和增长型创业公司在做微服务、大规模 DevOps、API 优先的团队——那是 2015 年。而另一边，有公司的表上有七十 TB 的数据要处理。这种落差让他积累了别人没有的经验。

但真正的认知转变发生在 Serverless 时期。

一开始他以为这全是技术问题：换个思路、换语言——当年 Java 在 Serverless 上表现不好，你得用 Go、Python 或 Node.js。对小团队来说，这确实全是技术。但当你要琢磨"这对一万个开发者怎么运作"的时候，大部分问题变成了组织转型。

"如果有一百个人，他们的工作就是盯着 Web 服务器重启东西，Serverless 把这些全接管了，你什么都不用做了。那你怎么过渡到重新定位、重新培训？"

他最长的一段时期——差不多四年——做的事情是：帮组织审视自己的人才和团队，思考社区建设、核心工程，用更小的团队、不同的方式组建团队。他能做到"给我三个人，六个月出 MVP，上线跑起来，然后推广到整个组织"——这在企业环境里原本不可想象，因为通常要花好几年，而大部分时间不是写代码，是协调、说服利益相关者。

这段经历他前后看了大概三四百家公司。这让他后来做 Agent 工作流时有了一个关键视角：这从来不只是技术问题。

两亿 Token 的学费：Agent 全权负责会破产

当 Agent 真正进入开发流程后，Hetal 先踩了一个大坑：让 Agent 全权负责重构，烧掉了两亿 Token。

这个数字背后是领导层必然到来的质疑："我需要一个月多付五千美元请一个工程师来干活？这笔账根本算不过来。"

对大公司来说这只是零花钱，但当你有一千四百名工程师时，这笔账很快就显现出来了。

他的解法不是不用 Agent，而是分层用模型——这也是他反复强调的"选最适合工作的工具，你不会想一直用同一个"：

  • SOTA 模型（最贵）：只用来理解、探索、规划。禁止创建任何文件，创建东西之前必须先请求许可，有钩子可以阻止它。在规划方面，这类超大模型极其高效。
  • 中档模型：进入实施阶段后使用，取决于规划内容的复杂度。
  • 小型开放权重模型：做一轮又一轮的审查。非常高效，财务部门会很高兴。

"我们现在还在摸索，但不会再进入那种对什么都用、Token 拉满的阶段。"他特别提到，最终的成本一定会来——当领导层发现为工程师每月多付几千块、而 Agent 账单还在涨的时候。

平台工程的角色：铺"康庄大道"，而不是强制

一千四百名工程师，怎么让他们都按合理的方式用 Agent？Hetal 团队的做法很亚马逊：平台工程组织负责铺路，但不强制。

他们现在的核心问题就是：在 Agent 时代，SDLC 应该长什么样？"我们要铺出什么样的康庄大道？那些我们确定可行的路。但永远不会只有一条康庄大道——他会根据不同的画像、不同的应用场景铺出不同的路。"

欺诈检测这种关键业务流，你不会为它省 Token；但一个内部 Webhook 工具，就没必要让最贵的模型跑。

具体怎么落地？他们盯住组织里的"定居者"——那些在探索新东西的人，密切关注什么有效、什么是炒作、什么不行。有了经验之后，再拉两三个团队做实验。比如 OpenSpec：在部分场景能用，但大部分场景根本跑不起来，因为他们有一个巨大的 monorepo。OpenSpec 默认所有东西都在顶层文件夹，没有在 monorepo 里工作的概念；当成百上千的开发者都在动这些代码，冲突就来了。所以他们的工作是从限制的角度想：怎么让一部分开发者先跑起来，再一步步挪到更大的 monorepo 上。

这里他用了云计算的类比：AWS 让 Lambda 客户"可以随时跑十万个容器"，但当客户真的成亿地增长时，你得做容量规划——你第一个应用凭什么需要十万个容器？限制本身就是一道软护栏。 当工程师的用量触到上限（比如只用 SOTA 模型、出到上线），那就是开启教育性对话的契机："让我了解一下你实际是怎么用的？"——这更像 IT 服务，而不是平台工程式的强制。

对抗性评审：没有伤疤的工程师怎么防 Agent 撒谎

访谈里有一个很扎心的问题：怎么防止 Agent"基本上对我撒谎"，伪造自己跑了测试、甚至从网上复制粘贴结果？

Hetal 的答案是对抗性评审循环：用你的判断决定什么时候启动更低阶、能力更弱的模型来评审你正在做的工作——从安全角度、从客户角度评审。这甚至是他偶然发现的。从产品角度也能这么做：写一个 PRD，为你想争取的客户类型创建虚拟客户，让评审模型站在客户视角挑毛病，得到不同发现，找出共同点。

"它不会解决你没有批判性思维的问题，但它会降低风险。"就像架构师，你的主要角色不只是让周围的人都更聪明，还要降低决策的风险。

但对抗性评审替代不了经验。他承认，新工程师很难有这种前瞻性："那些入行不够久、犯的错不够多的工程师——我犯的错多到数不清，才能有这种眼光。说'Agent 你目前干得不错，但别这么做'。"

还有一句值得单独拿出来："复杂性永远不会消失，你只是把它推到别处去了。" 架构一开始好好的，Agent 改着改着变成了意大利面——你不想承担那个复杂性，就得把批判性思维放到流程里，把天平往自己这边挪。

苏格拉底式的工作流：让工程师自己"发现"答案

访谈最后一段最有意思。Hetal 提到一位做 Rust 的朋友（Prince Benjamin，一位他仰视的 Rust 天才），在研究怎么把工程设计的讨论结构化——像决策记录，但技术含量更高，可以用来喂给 Agent。那份文档非常亚马逊风格：把所有事情想得特别周全，你必须去回答，必须去写。

但他从开源社区知道：当人们看到这种文档时会害怕、会退缩，只做最少的功夫，或者直接用 ChatGPT、Gemini 随便写点东西交差——冷静的批判性思考被抛到脑后。

他的解法是苏格拉底式的：把模板、命令变成工作流的一部分。当你在做最初的头脑风暴、探索、打开规范的时候，就通过一个命令把那些问题嵌进去——把韧性考量、及时管理变成这些事情的一部分。工程师不知不觉就产出了那份完整文档，而他们自己都不知道这本来就是目标。

"就像开源工具：加个日志器，马上就有结构化日志；一旦你有了关联的概念，加个标志就行。到最后他们审查的时候会说：'哦，原来我一直在做这些，我自己都不知道。'"

这背后是行为心理学：如果你把最终结果直接给人们，结果很完美但他们不信任，那永远行不通；但如果你给人们工具，让他们自己创造出那个最终结果，他们就会建立信念——因为他们的批判性思维被用上了，他们通过动手做建立信念，然后真的相信那个结果。 突然间，你就有了自动的认同。

为什么现在正是换一种做法的时候

"我们现在的很多学习、甚至我们沟通的东西，都太新鲜了，不去尝试、不去实验、不去学习，那太可惜了。早年的软件工程没有这么多创新。"

Hetal 说这话时带着明显的兴奋："经验越多，积累的教条也越多。而到了这个时代，你会发现，其实我们可以换一种做法。"他承认没有人对这一切有最终答案——"不然我们早就把它卖掉了"。

Agent 应该增强工程师，而不是替代判断。但在那之前，你首先得用那些硬技能增强自己——"你得知道他们在撒谎，他们会给出次优的结果"——然后才是放大。

这正是这场对话最反直觉的地方：一个每天和 Agent 打交道的 AWS 老兵，最后给出的核心建议不是更多自动化，而是更多批判性思维、更多经验积累、更多"犯过的错"。Agent 把开发流程的机械部分全部接管之后，剩下的恰恰是最难自动化的部分：判断。

值得带走的几点

  • 两亿 Token 的教训：让 Agent 全权负责重构会破产。分层用模型——SOTA 规划、中档实施、小模型审查——是控制成本的关键。
  • Agent 时代的 SDLC 是组织问题，不是技术问题：和 Serverless 当年一样，真正的瓶颈是团队怎么重组、怎么重新定位，而不是换哪个模型。
  • 平台工程铺"康庄大道"而不是发命令：靠盯住组织里的"定居者"积累经验，再小范围实验，用预算上限开启教育性对话，而不是强制统一。
  • 对抗性评审是防 Agent 撒谎的实用手段：让更低阶的模型评审高阶模型的工作，从安全、客户、产品多角度挑错，降低决策风险。
  • 复杂性不会消失，只会被推到别处：Agent 改出来的意大利面架构是你的责任，批判性思维必须前置到流程里。
  • 给工具而不是给结果：苏格拉底式地把问题嵌进工作流，让工程师自己"发现"答案，他们才会真正相信并执行。

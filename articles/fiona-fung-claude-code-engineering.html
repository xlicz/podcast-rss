Anthropic 工程主管 Fiona Fung：当编程不再是瓶颈，什么才是？

副标题：从打孔卡到 AI 智能体，25 年工程师生涯的亲历者告诉你——Anthropic 工程师每人每季度产出 8 倍代码之后，软件工程的工作本质已经变了

Fiona Fung 的故事要从 IBM 的一台终端机讲起。那时候她用 Vim 写代码，连 IDE 是什么都不知道。二十多年后，她坐在 Anthropic 的办公室里，管理着 Claude Code 和 Cowork 背后的团队——这两个产品正在让"编程"这件事本身从人类手中彻底转移给 AI。

但真正让人震撼的不是她的履历，而是一组数字。

Lenny Raczkiewski 在播客里打开了一张图。图上是一条平静了很多年、然后突然垂直上升的曲线。Anthropic 的工程师，现在每个季度平均产出的代码量，是 2021 到 2025 年间的 8 倍。

Fiona 对此的解释只有一句话："编程已经不再是瓶颈。"

从打孔卡到 Claude Code：一个 25 年工程师的进化论

Fiona 的职业生涯本身就是软件工程历史的缩影。"我在 IBM 做 DB2，在操作系统服务团队。那时候我觉得，越往底层走，越接近操作系统，就越硬核，也能学到更多。"

后来加入 Microsoft 做 Visual Studio，她甚至不知道 IDE 是什么——"我问经理，Visual Studio 这个名字听起来像是一个更好的画图软件吗？"但正是这段经历让她爱上了 dogfooding（用自己的产品来构建产品本身）。"我用 VS 编辑器来构建 VS 编辑器，我最想做的就是给自己和队友创造一种用起来很愉快的体验。"

Fiona 提醒了一个今天的工程师很容易忘记的事实："那时候我们把软件刻在 CD 上发布。截止日期非常硬——你必须确保软件准备好了，交给制造环节，然后他们再刻到 CD 上，最后放到货架上卖。" 因为工程时间是极其宝贵的资源，所以你会做更多规划，确保把有限的时间用到最好。

"现在我们在 Claude Code 和 Cowork 上看到的变化是，编程不再是瓶颈。所以现在问题变成了：瓶颈转移到哪里了？"

8x 代码量之后：新的瓶颈在哪里？

当代码产出增长 8 倍，旧的约束消失，新的约束立刻浮现。Fiona 看到的第一个新瓶颈是验证。

"不只是更多人在提交代码，而且是来自不同职能的人都在提交代码——工程师、设计师、产品经理，团队里的每个人都在提交。同时吞吐量又非常高。那我们该怎么思考验证？"

她的团队给出的答案是：把规范放进代码仓库。 "你给 Claude 一个框架，它很擅长按这个框架去验证。如果你有一段说明能说清楚什么算好，就把它放进 repo。这样 Claude Code 的代码审查就能确认现在的代码是不是还符合你当初设定的目标。"

但这不仅仅是技术问题。Fiona 提出了一个更根本的转变："以前工程时间是特别宝贵的资源。现在编程被自动化了，我们该把宝贵的工程时间用到什么地方？"

她的答案是——让工程师变得更像产品人。

两种人：Anthropic 现在招什么样的工程师？

Fiona 在演讲里把 Anthropic 现在看重的工程师分成两类，这个框架非常清晰：

第一类：有产品感的创意型构建者。 "这类人通常会说，我真的很喜欢某个产品，我有一个想法，然后他们就把它做出来。接着他们会一直看反馈，不断迭代，打磨，确保产品体验让人愉悦，从头到尾拥有这个产品。"

第二类：能处理难题的深度系统专家。 "我刚加入 Claude Code 的时候，我们有很棒的产品通才，后来我意识到我们缺少有系统背景的人——尤其是分布式系统。凡是涉及'信任但要验证'的部分，都要特别关注。模型真的很强，但还有很多地方仍然需要验证。"

这个二分法的底层逻辑非常清晰：AI 解决了"能不能做"的问题，剩下来的核心能力是"该做什么"和"怎么做对"。 前者需要产品感，后者需要深度领域知识。

TDD 的复仇：那些古老的原则，AI 让它们真正高效了

有一个细节很有意思。Fiona 回忆她在 Claude Code 上修的第一个 bug："我记得我问 Claude，我想做测试驱动开发。先帮我写测试，确保它会失败，然后我们再去修复，最后让测试通过。"

测试驱动开发（TDD）在 2000 年代曾经很火，但很少有人真正坚持——Fiona 自己的原话是"感觉像是必须先把西兰花吃掉"。但 AI 改变了这个等式。

"以前生成测试对我来说，就像必须付的一笔税。现在这件事自动化了。你甚至可以重新审视很多已经存在很久的原则，只是因为现在有模型能帮你做更多工作，这些原则可能真的变得更高效了。"

这是一个被低估的观察。很多工程原则在人类手工执行的年代因为成本太高而被放弃。当 AI 把执行成本降到接近零，这些原则反而是最先回归的。

角色边界的消融：产品经理在写代码，工程师在做产品

Fiona 描述的变化是双向的。工程师越来越像产品经理，产品经理越来越像工程师。

"如果 PM 有一个想法，现在不再一定卡在等工程资源上。我们的一些 PM 也会卷起袖子，帮忙实现一些功能。比如我们想做某件事，但当时工程师没法接的时候。"

但这反过来也意味着："所有跟编程相邻的角色都在变化。" 设计、数据科学——Fiona 认为这些是下一个被 AI 深度渗透的领域。

Lenny 讲了一个数据科学家的故事：现在很多人用 AI 自己做分析，然后拿给数据科学家说"这是我做的分析，能不能确认一下对不对？"结果有一半时间是不对的。数据科学家的工作从"做分析"变成了"审查 AI 生成的分析"。

这恰好回到 Fiona 的核心观点：验证能力正在成为比执行能力更稀缺的资源。

高能动性，高责任感

Fiona 反复提到的一个概念是 agency（能动性），但她加了一个重要的限定条件。

"看起来做得最好的人都是最主动、最积极、最有高能动性的人。我们说高能动性也意味着高责任感。重点是要确保大家有自由去写代码，但同时也要问清楚对应的责任是什么——你想解决的问题假设是什么？"

在 AI 大幅降低执行门槛之后，能动性的价值确实被放大了。但 Fiona 的洞见在于：如果没有配对的判断力和责任感，更高的能动性只会产出更多垃圾代码。 而且速度更快。

她把这个理念浓缩成一句话："犯错可以，但要犯新的错误，这样我们才一直在学习。如果你的目标是零错误，那可能说明你动得不够快。"

恐惧、抵制与成长型思维：AI 时代的两极分化

Lenny 问了一个很尖锐的问题："你看到那些做得很好的人和那些很沮丧、一直抗拒的人之间，有什么共同差异？"

Fiona 的回答直接指向了 成长型思维。"把你带到今天这个位置的方法可能以后就不再适用了。这真的很难，因为我们每个人走到今天都是靠某种做事方式。你会想，等等，我到目前为止都挺成功的，你现在让我改变那些让我成功的东西？"

对于那些感到恐惧的人，她的建议非常具体："只要有恐惧存在，我的建议就是靠近它，然后问自己：我能做什么？哪些事情在我的掌控之内？这件事不是发生在你身上，而是为了你发生吗？"

她还补充了一个观察，解释了为什么很多资深工程师尤其难以适应："他们会说，你看，它不行，你看这些问题。但他们很难真正理解这种指数级改进的速度。以前我试过自动化某件事，当时 Claude 还不够好，但到了下一个模型，可能它就够好了。所以要经常回头想想，以前没跑通的东西现在值不值得再试一次。"

规划在 AI 时代的死与生：从六个月路线图到 JIT

Fiona 分享了她在 Anthropic 学到的第一件大事：扔掉六个月路线图。

"我刚加入 Cloud Code 时想，也许我们应该做一个六个月路线图文档，但要做得非常轻量。三个月之后我意识到——等等，我们后来还看过它吗？因为太多事情都变了。"

她现在用的是一个叫"JIT 规划"（即时规划）的方法：一个简单的表格，列出下个月的优先级，每周快速检查一次——这些还是我们的优先级吗？ 没有长篇文档，没有复杂的流程。

"这个领域变化太快了。我从来不希望有人要更新表格时感觉像被加了一项负担。"她甚至还在思考如何把规划本身进一步自动化。

但她也保留了一些长期结构：团队每六个月聚一次，提出一些主题方向。"但关键还是要持续把握脉搏，因为这些主题本身也会变。外部环境一变，变化就会非常快。"

这种"轻量规划 + 高频检视"的模式，可能是 AI 时代最适合快速迭代团队的管理范式。它不是没有规划，而是承认规划的保质期在急剧缩短。

孤独的 AI 工程师：为什么要办"两两编程午餐"

Fiona 注意到了一个意想不到的副作用。当每个人都开始大量跟自己的智能体一起工作时，"这种工作方式可能会变得有点孤独。"

"因为我们团队里每个人使用 Claude Code 和 Cowork 的方式都不一样，所以我们开始做两两编程午餐。每次看别人工作，我自己也会学到东西。"

这和传统意义上的结对编程不同——更像是"平行游戏"。"你们坐在彼此旁边工作，但各自做自己的东西。但哪怕只是看别人怎么构建东西，也非常有价值。"

另一个她强调的仪式是黑客松。"确保我们还是作为一个团队在互动——这是我们很喜欢做的一件事。"

这个观察很有价值。当 AI 让你不再需要和同事讨论技术细节就能完成任务时，学习的机会也在流失。刻意创造社交化的技术场景，正在从 nice-to-have 变成必须刻意维护的东西。

往下再点一层：新一代工程师怎么学习？

聊到工程教育和人才培养时，Fiona 坦承了一个她还没有答案的问题。

"我们怎么培养下一代？你和我走上工程这条路的方式和现在已经非常不一样了。学生一毕业就要想办法快进到某个阶段。"

她的底线是：不管你做什么工作，都还是要理解架构，理解改动。 "这又回到那句话——信任但要验证。也许有一天这不再重要，但按照我们现在的节奏，我其实仍然觉得理解你所依赖的那一层很重要。"

她用了一个有意思的比喻：她的前经理最早做软件工程的时候用打孔卡，现在在用 Claude Code 构建各种东西。"这是一段多么了不起的职业生涯——从打孔卡一路走到现在。所以也许我们要思考的是，哪些东西仍然重要，哪些东西的重要性会变化。"

她的猜想是：重要的东西会随着时间转移，问题在于你怎么建立相应的熟练度。

文化是活的东西：招人再多，别丢了团队的纤维

被问到"什么事让你晚上睡不着"时，Fiona 的回答不是技术路线、不是竞争对手，而是团队文化。

"文化是一个活的东西，它不是贴在墙上的一张海报。它体现在我们怎么对待彼此，怎么支持彼此。多元视角非常重要，这样我们才能公开的、健康的、诚实的辩论。"

她特别在意一件事：管理者要能说出哪里不对。 "说到什么事情会让我晚上睡不着，我最怕的就是——特别是一个人处在管理岗位上，我问他说最近怎么样？他说一切都很好。我心里会想，天哪，不可能很好。"

"你知道那个梗图吗？一只狗坐在着火的房间里喝咖啡，说一切都好。那就是我最怕看到的场景。"

她还分享了 Claude Code 团队文化里一个很重要的点：明确允许大家干掉那些已经不再服务我们的流程。 "先挑一件事——这个流程可能是你特别不想做的，或者噪音特别多，或者成本很高，或者非常手工。然后问自己：它现在还在实现原来的目的吗？"

从小企业到毛线店：一个工程领导者的另一面

整场对话最动人的部分，可能来自一个完全出乎意料的方向。

Fiona 聊到她出生在香港、在加拿大长大、小时候一句英语都不会的经历。她的奶奶从香港搬来照顾她，但在那个新国家非常孤立——直到她们发现了一家小小的毛线店，店主是一位会说粤语的女士。"那个夏天，我们每周都会去那家毛线店。我奶奶在那里找到了她的编织小圈子。"

这份记忆后来变成了一个执念。当 Fiona 用 Cowork 处理自己的差旅报销时，她突然想到她的小企业主朋友们。"他们真的非常拼，工作特别辛苦，利润率可能很薄。我有时候看到朋友坐在吧台边，面前堆着一罗账单，做的全是开发票、报销这些事。"

于是她开始帮他们上手 Cowork，看他们走通整个流程。"我帮他们只是因为我关心他们，我也希望他们能继续经营下去。"

她依然在编织——Boris 爆料说，在一些非常重要的会议里，经常能听到背景里 Fiona 织毛衣的咔嗒声。她的梦想是开一家毛线店，用她外婆的名字命名，然后围绕它建立一个社区。

"编织基本上就两种针法，下针和上针，有点像零和一。我有点像一个编译器——编织的时候就像在生成一个可执行文件。"

从打孔卡到 AI agent，从 Visual Studio 到 Claude Code，从外婆教的编织到如今穿着自己织的上衣开会——Fiona Fung 的故事里有一条隐藏的线索：创造本身，比工具重要得多。

  • 编程不再是瓶颈——验证才是。 Anthropic 工程师每人每季度代码产出已是 2025 年前的 8 倍。当 AI 生成代码接近零成本，判断什么是对的、什么值得做，才是人类的核心价值。
  • 招两种人：产品型构建者和系统深度专家。 前者负责"该做什么"，后者负责"怎么做对"。AI 解决的是中间层。
  • TDD 回来了——被 AI 救活的。 很多工程原则在手工执行年代因成本太高被放弃。当 AI 把成本降下来，这些原则反而最先回归。
  • 高能动性必须配高责任感。 执行门槛越低，判断力越稀缺。能动性不加约束，只会产生更多更快的垃圾。
  • 成长型思维是 AI 时代的生存技能。 把你带到今天的做事方式可能明天就不再适用。恐惧是正常的，靠近它，然后问自己：我能做什么？
  • 规划从"六个月路线图"变成"一月表格 + 周检"。 承认规划的保质期在急剧缩短，但保留方向性的主题。
  • 刻意对抗 AI 带来的孤独感。 两两编程午餐、黑客松——学习机会正在从日常工作里消失，需要刻意创造社交化的技术场景。
  • 文化不能自动化。 在增长、招聘、变化的疯狂速度中，文化是唯一需要人工持续维护的东西。允许团队"干掉不再服务的流程"。
  • 下一代工程师仍然需要理解底层。 信任但要验证——这个原则现在比任何时候都重要。不管工具多强，你还是得知道你在依赖什么。

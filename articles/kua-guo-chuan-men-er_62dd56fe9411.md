# 一群人对着麦克风轻声说话，是这家 AI 公司最重要的工程实践

**Basis 的 agent 能自主运行几个小时、有时是几天，端到端做完一份纳税申报表。它的联合创始人 Mitch Troyanovsky 讲了他们的做法：把上下文当成运行时的训练数据、用行为规范代替边界枚举、不去动模型权重，以及为什么熬过 The Bitter Lesson 的不会是技术护城河。**

走进 Basis 的办公室，你会看到一群人对着麦克风非常小声地说话。不是语音输入法，也不是在演示产品——这是日常工程习惯。他们做的活也不是"帮我写个函数"：一份纳税申报表，一个人要做二十多小时的工作，涉及五百到一千份文档、几千个推理步骤。The Mad Podcast 主持人 Matt Turck（FirstMark 合伙人）和 Basis 联合创始人 Mitch Troyanovsky 聊的就是这件事该怎么干，其中最值钱的是几个反直觉的判断。

## 对着麦克风轻声细语，不是怪癖

The Information 的记者 Stephanie Palazzolo 去 Basis 拍过一段视频，画面里就是一群人对着麦克风非常小声地说话。Mitch 的解释很直接：说话比写下来快太多。写下来的时候，你其实是在试图总结脑子里那些乱七八糟的想法，那才特别花时间；而口语的粗糙对同事是不礼貌的，对 LLM 反而更好——它们不在乎，甚至更喜欢。麦克风能在极低音量下完整捕捉声音，因为办公室里还坐着别人。新同事刚来觉得奇怪，一两个月后就回不去了。口述的对象是各人自己在用的工具，Codex、Claude、Cursor 都有，而且不只工程岗——全公司都这样。

> 你得给它尽可能多的上下文。因为它本质上总是会缺少某些上下文。

## 上下文不是 prompt，是运行时的训练数据

多数人想到"上下文"，脑子里浮现的是：我写一段英文，告诉模型该做什么。Mitch 认为这是错误的心智框架，他更愿意把它当作训练数据——只不过你是在运行时训练模型。因为模型在推理时学习，所需的数据总量比后训练低好几个数量级，所以你有可能把每一条数据手工打磨到最高质量。

数据只是一环，此外还有 harness、有哪些工具、环境、选了哪个模型。关键区别在于：这份信号用来改进的是整个 agent 系统，需要的数据规模远小于拿同一份信号去对底层模型做强化学习。这也是他们不动权重的理由——模型在自我编排上的进步，带来的性能提升远超直接更新模型。

## 一百个评估全过，也说明不了它能干活

编程是第一个跑通的自主 agent 场景，运行时能验证只是入场券——可验证奖励解决不了的那部分是：一年半前的编程 agent 能实现你交代的功能，却没有品味，通过世界上所有的测试也不代表它把应用搭对、数据库建好、文件拆得合理。**编程终究是主观的，是一门艺术，你没法用可验证奖励去解决一门艺术。**

会计这行没有这么便宜的事。如果工程师跑来告诉你"我所有测试都过了"，那意味着他把数据库架构建对了吗？不一定。Basis 面对的是几千步的长轨迹，就算一百个评估全部通过——数字对得上、LLM 当裁判按评分准则打分——你敢说它能泛化到生产环境吗？他们的答案是不能。

解法来自一个类比：**人类早就习惯跟非确定性系统打交道，只不过那些系统通常是他们的同事，而不是他们的电脑。** 公司也好、流程也好，核心问题一直是"你怎么设计一个系统，让一群非确定性的实体协同解决一个问题"。意识到这点，agent 设计就不再是新问题，而是组织设计的老问题换了个对象。

于是他们去看会计师怎么做申报：有验证步骤、有独立复核、有可确定性验证的东西——试算平衡表加起来必须等于零，Excel 里不能有报错。这些检查对人显而易见，但你得确保它们被正确编码；剩下那些不能确定性验证、但会计师一眼就知道不对的（标签页被删掉、引用漏了），可以做成验证器，用评判模型取信号。

最锋利的一句是关于及格线的：如果一个人一百次里一百次都答对了，但他只是靠查维基百科才做对的，公司根本不会雇他。真实的税务会计师不信预训练知识，也不信你读了篇博客，他们要求引用主要来源。所以 Basis 的 agent 必须去查法规原文——全对不够，路径也得对。

## 行为规范：写给人看的规格，不给 agent 看

两年前，Mitch 和联合创始人 Matt 聊 AutoGPT 时提出过一个概念。当时还没有今天意义上的完整 agent，但你已经得想清楚：在这个岔路口，你希望它做什么样的选择？最初的名字更长，大意是"源层面上的行为"——定义的不是某条轨迹上的动作，而是横跨所有轨迹的行为。后来简化成 behavior，形态是一个 Markdown 文件，里面可以非常具体（"总是去看 IRS 网站"），也可以是一条通用直觉（"把 PowerPoint 交给用户之前先渲染成图片，你就知道有没有格式问题"）。

它有两个身份：既是规格说明，也是评分标准。除了给 agent 打分或构造奖励信号，它还有个被低估的作用——对齐人类。"你希望 agent 怎么表现"本质上是主观问题，一个组织需要就它达成共识并写下来。

但这份文件不展示给 agent 看。这个选择直接通向 The Bitter Lesson：如果未来你只要说"我要这些行为"模型就能做到，整套上下文工程会整个消失。Mitch 认为它一定会被吞掉，"没有疑问"，大概是五年以内——不是两年以内。

写多具体是产品判断。写得太细就脆弱——他举机场告示牌为例：不要带枪、不要带刀、不要带剑、不要带这个那个，列了三十样；你可以列五十条脆弱规则，也可以写出一条恰到好处的抽象，刚好把它全部覆盖。擅长构建 agent 的人都知道，边缘情况下给原则、给"为什么"、给更多上下文，让 agent 自己搞清楚，效果要好得多。要不要每次交付 PowerPoint 前都拍张照片？三十秒跑完的 agent 拍照变一分钟，不值；二十分钟的 agent 只多花三十秒，那就每次都拍。加上维护成本——行为写下来就得保持最新，否则系统里会出现矛盾的"真值"——所以规范越少越好，只挑少数几个对泛化影响最大的。

这里有个容易被忽略的权衡：定了流程，你就放弃了"AI 绕过流程直接做得更好"的可能性。那如果工程师拿着一千行的 PR 说"我现在就要合并进生产环境"，而他真的比 CTO 的方案更好呢？答案仍然是那样也不行。客户买的从来不是"史上最好的一份纳税申报"，而是一份能放心签字、稳定可靠的东西。就像对人一样：信任慢慢积累，自主权逐步授予。

## 谁来评判 judge

行为评判成本相当高，因为它本身就是一个 agent——必须看整条轨迹，而不是读一段输出。一条长时程轨迹里可能有很多子 agent 的轨迹；一个深度七层的系统摆在评判器面前，第一个问题是：我到底在评判谁？根节点做对了，还是某一层做错了？你需要某种"地图"，也要调好提示词，让它知道该去哪看、行为被触发的条件是什么。现实地说，他们没那么多资源把每个评判器打磨到完美；更可行的方向是像 Braintrust 这类公司在推进的：把轨迹标注拆解得更好，过滤出可能相关的片段再交给评判器，而不是每次吞下整条轨迹。

## 最硬的约束是数据，不是模型

他做了个思想实验：假设你能拿到全国每一份真实的纳税申报表——出于隐私不可能，但假设有。用它们验证 agent 干得怎么样，这个数据量跟合成数学题相比依然微不足道。别人能合成几十万、几百万道数学题，你没法合成几十万份纳税申报表——因为你合成的不是文本，而是轨迹，而轨迹必须真实且多样。

第二重约束是反馈回路的长度。一份 Form 1065，一个人可能要花二十多小时的实际工作时间，复杂申报还要长得多；即使你拥有全世界所有数据，也凑不出训练一个真正优秀的 agent 所需要的反馈回路。再具体一点：编制一份申报表，很容易面对五百到一千份文档，每份都要做大量不同的研究，还要理解它们互相之间怎么映射，最后编进一个大型 Excel 工作簿——推理步骤轻松几千步；如果为不同的事派生子 agent（这基本是必须做的），步骤数还会涨。

## 本体：agent 的文件夹就是它的记忆

一个常被忽略的差异：编程 agent 的"运行时训练数据"不归你所有——它就是那个代码仓库。所以同一个 Codex 在 A 仓库表现平平，在 B 仓库表现惊艳，差别可能全在仓库本身：有没有好的 skills、有没有清晰的操作上下文、有没有互相矛盾的地方。非编程领域正好相反：Basis 的 agent 看到的大部分数据是 Basis 拥有的，那就必须被精心设计。

这就是 ontology（本体）的位置。它可以是结构化的文件系统、图数据库、节点和连接器，也可以挂嵌入和各种元数据；随着推理成本往下走，越来越多整理工作可以直接交给模型。但本体不只是一套文件夹结构，它同时是语言——定义对象和概念是什么，因为你的系统是在运行时被"训练"的，你必须确保概念不会互相打架。

时程长度还会改变本体的形态：跑几个小时的 agent 留下的可能只是几条笔记，跑几个月的 agent 留下的是一整个文件夹——它经历过的全部上下文都被压缩沉淀在那里，新 agent 从这份高度压缩的上下文启动，必须把自己恢复到"我经历过这一切"的心智状态。

内部用 agent 的关键只有一条：必须清楚什么是权威的、什么不是。你不能让一个 agent 从这个人这里听一种销售策略、从另一个人那里听到另一种。他有个很妙的类比：新人可以去听所有的 Gong 录音，但如果你听的是两年前的录音，你会得到大量背景，却完全不知道今天的策略是什么。必须有一份权威文档，而且像代码一样持续更新。有人问过他，给 agent 的内部文档该不该像代码库一样对待，他的回答是：删掉关键段落，agent 就崩了，就像删掉一行代码。他还吐槽了行业里一个滑稽现象——有人对一段抽象得不够好的代码文件大惊小怪，可他们给 agent 的上下文简直是一团糟：英文影响运行时表现，代码不影响。

## 苦涩的教训会来，所以护城河不在技术

关于"自建强化学习是不是护城河"，Mitch 的回答干脆得近乎扫兴：技术护城河不是真正的护城河。Basis 的长期价值里，没有任何一部分来自"我们发现了别人没发现的秘密 RL 技巧"。现在重要的是他们确实擅长构建可靠、能上生产的长时程 agent，这让他们赢得市场份额、深度嵌入客户——也解释了为什么跑这么快：他们要在 AGI 到来之前把业务铺开。他举了一个在位者的例子：那家公司的护城河跟技术毫无关系，靠的是商业地位、它掌握的权利、它占据的工作流、深度嵌入带来的一切。技术只是暂时的撬动点，让三年前还不存在的公司突然能做这些活。

至于为什么不动权重：RL 真正难的是决定奖励函数是什么、以及怎么把奖励分配到实际发生的事情上——难的是信号开发，不是信号怎么扩散。他也不相信"把预训练算力加上去、再把基于完美可验证奖励的后训练加上去，就会突然出现一个能可靠完成纳税申报的模型"：就算做出很好的版本，问题也不是它做得好不好，而是它能不能达到"和一个它一起干活的人所期望的质量、可靠性、可扩展性"。

## 对 agent 开发者，他只有一条建议

人很容易看着世界变化这么快，就觉得一切都在这里冒一个、那里冒一个，像在 Twitter 上得了多动症，然后怀疑自己没法做第一性原理的判断。Mitch 的建议是把新世界看成一次底层的范式转变——就像云计算那样——然后推演：如果智能变强了 X 倍，或者没有变强，那意味着什么？这样能构建出连贯得多的系统，也能做出好得多的战略决策。

他甚至认为，从 Opus 3 到现在没有发生过范式级别的转变。他对论文的态度也很克制：读有用，但很多人在上面用力过猛；建立 LLM 直觉最好的方式是大量在自己的工作里用它们，然后不断追问"真正的限制因素是什么"——它没按我想要的方式做，是它不够聪明吗？大概不是，它们已经聪明了好一阵子。他在面试里也看到同样的规律：直觉最好的人里很多有机器学习背景，但没背景的那些，往往是特别擅长自动化自己工作的人。

## 最后

回看那个对着麦克风轻声说话的办公室：它存在，是因为写下来太慢、太失真，而 agent 需要的恰恰是未经压缩的原始上下文。而 Mitch 对这整套做法的判断是——它会在五年内过时。

但今天的客户要的不是史上最好的纳税申报表，而是一份能签字、能复核、能被信任的表。这两件事之间隔着的东西——过程、独立复核、主要来源、可以稳定依赖的行为——恰恰是模型变得更强之后也不会自动消失的那部分价值。

## 文末要点

- **上下文不是提示词，是运行时的训练数据。** 模型在推理时学习，所需数据量比后训练低几个数量级，所以你有可能把每一条上下文都手工打磨到最高质量。全公司对着麦克风轻声口述，就是因为写下来等于提前做了一次失真压缩。
- **可验证奖励只解释了编程成功的一小部分。** 运行时能验证、成本低、纯文本是入场券；但编程终究是艺术，通过所有测试也不代表架构做对了，真正的大头是高质量训练数据的量和质。
- **结果导向的评估不够用。** 一百个评估全过也证明不了泛化；人类本来就习惯跟非确定性实体协作，所以验证设计应该照抄人怎么组织工作：确定性检查，加上"会计师一眼就看出不对"这类验证器。
- **行为规范既是规格说明也是评分标准，而且不展示给 agent。** 它同时用来对齐人类和给 agent 打分；不展示是为了给 The Bitter Lesson 留后路——Mitch 判断整套上下文工程会在五年内被模型吞掉。
- **护城河是商业护城河。** 长期价值里没有一部分来自秘密 RL 技巧，真正积累的是商业地位、掌握的权利、占据的工作流和深度嵌入。
- **最硬的约束是数据和反馈回路。** 合成的不是文本而是轨迹，轨迹必须真实且多样；一份 Form 1065 要人做二十多小时、几千个推理步骤，即使拥有全世界的数据也凑不出需要的反馈回路。
- **把新世界当云计算那样的范式转变，然后推演"智能强 X 倍意味着什么"。** 范式其实没怎么变——在他看来 Opus 3 之后没有范式级别的转变，只是很多人读论文用力过猛。
